1. Ringkasan Sistem & Arsitektur

Intercloud Portal adalah portal admin & klien untuk operator ISP / Data-Center. Sistem mengintegrasikan penjualan, provisioning, NOC monitoring, penagihan otomatis, dan CRM ke dalam satu antarmuka dengan pembayaran online (Duitku) dan operasi jaringan MikroTik secara langsung.

1.1 Tumpukan Teknis

LapisanTeknologi
FrontendReact (Create React App) + Tailwind + shadcn/ui, di-serve statis oleh nginx
BackendFastAPI (Python 3.12) + uvicorn, dijalankan oleh supervisor
DatabaseMongoDB 7.0 / 8.0 (Motor async)
Reverse Proxynginx (HTTP 80 → HTTPS 443 via certbot) menuju backend 127.0.0.1:8001
Payment GatewayDuitku (satu-satunya) — Midtrans/Xendit dinonaktifkan by policy
Live OpsMikroTik RouterOS v6/v7 lewat API port 8728/8729
EmailPer-admin SMTP + IMAP (cPanel) — bukan SMTP global
SchedulerSatu instance APScheduler untuk semua cron (renewal, NOC probe, backup)

1.2 Struktur URL

  • / — Landing page publik (SEO, artikel, kontak)
  • /articles/<slug> — Halaman artikel + dynamic SEO render untuk bot crawler
  • /portal/login — Login (staff & client)
  • /portal/admin/* — Modul admin/staff (di-block via robots.txt)
  • /portal — Dashboard klien
  • /status — Halaman status publik (tanpa auth) menampilkan health per grup abstrak
  • /api/portal/* — Seluruh endpoint API (di-proxy nginx ke port 8001)
  • /sitemap.xml, /robots.txt — SEO artefak

1.3 Kebijakan Konfigurasi

Yang WAJIB dipatuhi selama UAT:
  • Pajak (PPN) selalu manual per dokumen. Nilai default settings.default_tax_percent hanya prefill, boleh diubah manual saat membuat invoice/quotation.
  • Payment gateway hanya Duitku. Tidak boleh ada CTA Midtrans/Xendit di UI klien.
  • Kredensial (API key, merchant code, password SMTP) tidak boleh muncul di UI, log, atau file .md. Field password selalu ter-mask pada respons GET.
  • Hanya satu instance APScheduler — tidak boleh ada scheduler tandingan.

2. Peran (Role) & Ringkasan Akses

Portal punya 8 peran (7 staff + 1 client). Menu & hak akses ditentukan oleh default_roles di ADMIN_MENU_CATALOG — bisa dioverride per user via menu_keys. Feature flag (can_delete_invoices, can_export_data, dll.) mengatur aksi granular.

2.2 Cara Kerja Feature Flag

Tiap user staff punya kolom menu_keys (override menu) dan feature_flags (override aksi). Admin dapat mengaktifkan / menonaktifkan kemampuan seperti can_delete_invoices, can_view_all_clients, can_impersonate_client per user dari halaman User Access.

UAT wajib menguji: ketika flag di-uncheck, endpoint terkait harus mengembalikan 403 Forbidden — bukan sekadar menyembunyikan tombol di UI.

3. Alur Kerja Bisnis End-to-End

3.1 Alur Order Baru (New Customer)

1 Pelanggan mendaftar di landing page → POST /auth/register (email + password + reCAPTCHA). Sistem kirim email welcome via per-admin SMTP.
2 Pelanggan login ke /portal → dashboard klien.
3 Pelanggan pilih paket di landing atau lewat portal → POST /client/orders membuat Order berstatus pending.
4 Sistem otomatis generate Invoice (nomor INV-YYYY-#####) dari order tersebut. Pajak prefill dari settings, tetap manual per invoice.
5 Pelanggan bayar via Duitku (klik "Pay Online") atau upload bukti transfer manual.
6 Callback Duitku /webhooks/duitku memverifikasi HMAC-SHA256 → set invoice paid → memicu email payment_received + auto-provisioning + reaktivasi service yang sempat suspended.
7 Service masuk status active. Untuk VPS/Colo: script provisioning MikroTik dijalankan oleh Support atau otomatis (bila flag can_run_provisioning aktif).

3.2 Alur Renewal Otomatis

Cron di APScheduler jalan setiap jam menit ke-20 (dan sekali saat startup) — memanggil run_renewal_invoice_sweep:

  1. Cek service dengan next_renewal ≤ hari-ini + settings.renewal_lead_days.
  2. Guard duplikat: invoice.service_id + renewal_period — invoice hanya dibuat sekali per siklus.
  3. Setelah insert sukses, next_renewal baru maju ke siklus berikut.
  4. Nomor invoice memakai counter atomik + retry pada DuplicateKeyError.
  5. Email invoice_created dikirim ke billing_emails klien.

Trigger manual (untuk UAT): POST /admin/billing/run-renewal-sweep.

3.3 Alur Ticket & Escalation

1 Klien buka ticket POST /client/tickets — pilih departemen (technical/billing/general/sales), prioritas, opsional device_id.
2 Ticket mendapat nomor TCK-YYYY-#####, status open.
3 Staff (support/admin/ticket_only) melihat di modul Tickets dan mengirim balasan POST /client/tickets/{tid}/replies. Status berubah menjadi awaiting_client atau tetap open.
4 Klien balas → status awaiting_staff. Riwayat pesan tersimpan lengkap dengan attachment.
5 Ticket ditutup oleh staff → status closed dan tercatat di audit_logs.

3.4 Alur Insiden NOC

1 Setiap 5 menit, run_noc_probe_sweep memprobe semua MikroTik device.
2 Sample uptime disimpan di noc_probes; state up/down current di noc_device_state.
3 Saat transisi UP↔DOWN (tidak setiap probe), event dicatat di noc_events dan email alert dikirim ke settings.noc_alert_recipients.
4 Halaman publik /status menampilkan agregat per grup abstrak (Core Network / Customer Edge / Peering). Tidak membocorkan nama device atau IP.

6. Alur Pembayaran (Duitku) & Renewal Otomatis

6.1 Konfigurasi Duitku

Kredensial disimpan di collection integrations (module=duitku, enabled=true). Tidak pernah hardcoded. Signature request: HMAC_SHA256(merchantCode + timestamp, apiKey). Callback verifikasi: HMAC-SHA256 utama + fallback MD5 legacy + merchantCode match.

6.2 Alur "Pay Online"

  1. Klien klik "Pay with Duitku" pada halaman invoice unpaid.
  2. Backend POST /client/invoices/{iid}/pay-online memanggil createInvoice Duitku (returnUrl wajib + expiryPeriod).
  3. Duitku respons paymentUrl → frontend buka di tab baru.
  4. Klien selesaikan pembayaran di halaman Duitku.
  5. Duitku POST callback ke /webhooks/duitku.
  6. Signature valid + status 00 & belum paid → transaksi diproses SEKALI:
    • Invoice → paid, payment_method=duitku, paid_at di-set.
    • Email payment_received dikirim.
    • Auto-provision order terkait (jika ada).
    • Reaktivasi service suspended karena invoice tersebut.
  7. Callback duplikat: respons {duplicate:true} tanpa efek ganda.
UAT wajib menguji:
  • Signature invalid → HTTP 400 dan invoice tidak berubah.
  • Callback dobel → tidak boleh ada duplikat email / reaktivasi ganda.
  • Tombol Midtrans / Xendit tidak muncul di UI kecuali flag enable_extra_payment_gateways di-ON (dan flag ini default OFF).

6.3 Renewal Sweep

APScheduler menjalankan run_renewal_invoice_sweep tiap jam menit ke-20. Setting yang mempengaruhi:

  • default_tax_percent — prefill pajak, tetap manual per invoice.
  • renewal_lead_days — berapa hari sebelum jatuh tempo invoice dibuat.

7. Operasional Jaringan — MikroTik, NOC, DCIM

7.1 Multi-Device MikroTik

Device disimpan di collection mikrotik_devices. Legacy fallback: bila tak ada device_id, sistem pakai integration mikrotik tunggal.

  • Test Connection (test-connection) — verifikasi kredensial.
  • Interfaces, traffic per interface, backup export.
  • Blackhole route — RouterOS v7 syntax (blackhole=yes). LIST menggunakan server-side filter (?blackhole=yes) supaya tidak stream full BGP table; mendukung prefix_filter.
  • Looking Glass — ping/traceroute dengan src_address, BGP route lookup longest-prefix.
  • Torch — traffic sampling per src/dst (perlu flag can_control_mikrotik).

7.2 NOC Monitor

  • Probe sweep tiap 5 menit — polling ke semua device.
  • Hanya transisi UP↔DOWN yang menghasilkan event (mencegah flap-storm).
  • Retention: probes lama di-rollup + dihapus; events tidak pernah dihapus oleh retention job.
  • Alert email ke settings.noc_alert_recipients; fallback ke semua user role=admin.

7.3 Public Status Page (/status)

  • Tanpa autentikasi — auto-refresh 60 s.
  • Data diagregasi per grup abstrak ("Core Network", "Customer Edge", "Peering & Transit") — konfigurabel dari admin.
  • Status global: operational / degraded / unknown.
  • Incident banner (bila dikonfigurasi) tampil di atas.
Wajib diuji: Raw JSON dari /api/portal/public/status tidak boleh membocorkan nama device, IP, atau topologi.

8. Keamanan, Audit Log & Kepatuhan

8.1 Autentikasi

  • Login JWT (bearer token) untuk staff & client.
  • Auto-block: default 10 gagal / 15 menit → banned 30 menit (konfigurabel di Security Settings).
  • Rate limit login 10/min per IP (X-Forwarded-For aware).
  • reCAPTCHA v3 / Cloudflare Turnstile pada login & register.
  • Password harus di-change pada login pertama bila flag must_change_password aktif.

8.2 Header Keamanan (nginx)

Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
X-Frame-Options: DENY
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=(), interest-cohort=()
Content-Security-Policy-Report-Only: (whitelist self + reCAPTCHA + Turnstile + fonts) + report-uri /api/csp-report
Cross-Origin-Opener-Policy: same-origin

8.3 Audit Log

Setiap aksi sensitif ditulis ke collection audit_logs lewat log_audit(db, ...). Field yang tercatat: actor, target, before, after, ip, user_agent, category, action, severity, created_at. Field secret (password, api_key, token, ...) di-redact otomatis.

Instrumented: user role/password change, delete user, admin password reset, billing/security settings update, integration upsert/delete, factory reset, backup restore, credit note create/apply/cancel, invoice paid-by-credit, status page config update.

8.4 Kebijakan Lain

  • robots.txt Disallow /portal/admin & /api/portal/admin.
  • Sitemap.xml — hanya URL publik (landing + articles).
  • 404 route — SPA fallback dengan meta robots noindex.
  • Server tokens off — versi nginx tidak dibocorkan.
  • Backup harian — cron /etc/cron.d/intercloud-daily-backup.

9. Skenario UAT — Checklist yang Harus Diverifikasi

Isi ceklis di bawah untuk setiap peran. Jika ada satu fail, UAT belum sign-off.

9.1 Auth & Onboarding

A-01 Admin login pertama dengan credential seed — dipaksa ganti password.
A-02 Register klien baru dengan reCAPTCHA valid → email welcome diterima di billing_emails.
A-03 10× login gagal dari 1 IP → percobaan ke-11 mendapat 429 & muncul di Security ▸ Blocked IPs.
A-04 Unblock IP dari admin → login berhasil lagi.
A-05 Change password: password lama tidak boleh dipakai lagi.

9.2 Peran & Menu

R-01 Sales login → hanya melihat klien yang di-assigned (bukan semua).
R-02 Sales PUT/DELETE klien milik sales lain → HTTP 403.
R-03 Finance melihat menu Finance, Invoices, Credit Notes, Assets.
R-04 Owner mencoba PUT apapun → HTTP 403 (read-only).
R-05 Ticket-only user hanya melihat menu Tickets + Dashboard.
R-06 Creative melihat Media Library, Content Calendar, UTM Builder.
R-07 Uncheck can_delete_invoices di user X → user X coba DELETE invoice → 403.

9.3 Sales & Billing

B-01 Buat Product baru, kategori valid → tampil di Catalog publik.
B-02 Klien order product → Order status pending + Invoice unpaid ter-generate otomatis.
B-03 Invoice PDF preview: logo 130 px, kolom bank transfer muncul untuk status unpaid.
B-04 Klien A tidak dapat mengakses invoice klien B (bahkan lewat URL langsung).
B-05 Tandai invoice overdue secara manual → status berubah, cron auto-mark tetap berjalan.
B-06 Buat Credit Note dengan auto_apply ≥ total invoice → invoice otomatis paid, service reactivated.
B-07 Credit Note apply melebihi total invoice → ditolak.
B-08 Quotation di-generate PDF, di-email ke klien.
B-09 Renewal Sweep manual (POST /admin/billing/run-renewal-sweep) → invoice renewal terbuat sekali per siklus.
B-10 Setting default_tax_percent di-set 11% → invoice baru prefill 11%, admin bisa ubah manual jadi 0 atau 12.

9.4 Pembayaran Duitku

P-01 Klien klik "Pay with Duitku" → dialihkan ke halaman payment Duitku.
P-02 Simulasi callback sukses (signature valid) → invoice paid, email diterima, service reactivated.
P-03 Callback signature invalid → HTTP 400, invoice tidak berubah.
P-04 Callback dobel identik → respons duplicate:true, tidak ada aksi ganda.
P-05 Tombol Midtrans / Xendit tidak muncul di UI klien (flag enable_extra_payment_gateways = OFF).

9.5 Tickets & Mail

T-01 Klien buka ticket → mendapat nomor TCK-YYYY-#####, muncul di list staff.
T-02 Support balas ticket → status awaiting_client, email notification terkirim.
T-03 Klien reply → status awaiting_staff.
T-04 Admin belum setup SMTP pribadi → tombol Compose di Webmail memunculkan pesan "Silakan setup SMTP dulu di Settings ▸ Email…" (bukan 500).
T-05 Setup Email → Test Connection: hasil per IMAP & SMTP tampil hijau/merah.
T-06 Reply email di Webmail memakai prefix "Re:" + kutip body asli.

9.6 MikroTik & NOC

N-01 Tambah device MikroTik → Test Connection sukses.
N-02 Add blackhole route (RouterOS v7) → tidak muncul TrapError "unknown parameter type".
N-03 List blackhole dengan prefix_filter → respons < 5 detik, tidak stream full BGP.
N-04 Looking-Glass ping dengan src_address → parameter terkirim ke RouterOS.
N-05 BGP route lookup untuk /32 → mengembalikan /24 covering (longest prefix).
N-06 Matikan device di lab → dalam 5–10 menit NOC device state jadi down, event tercatat, email alert diterima.
N-07 Public /status menampilkan grup degraded, tanpa nama device / IP di JSON.

9.7 Landing, SEO & Artikel

S-01 /sitemap.xml mengembalikan XML valid, semua artikel published tercantum.
S-02 /robots.txt berisi Disallow /portal/admin.
S-03 Curl /articles/<slug> dengan User-Agent Googlebot → HTML meta lengkap (title/description/canonical/JSON-LD).
S-04 Setiap <img> artikel punya alt text (fallback ke title).
S-05 Favicon SVG + apple-touch-icon dapat diakses.

9.8 Data Integrity

D-01 Buat 20 invoice paralel (bulk) → semua nomor unik (INV-YYYY-#####), tidak ada 500 karena unique index.
D-02 Hapus kategori yang masih dipakai product → ditolak dengan pesan yang jelas.
D-03 Ubah slug kategori → semua product terkait ikut ter-cascade.
D-04 Backup harian menghasilkan file di backups collection; Factory Reset tetap membuat safety snapshot.
D-05 Audit Log memuat before/after untuk setiap perubahan role/user/security.

9.9 Kepatuhan Kebijakan

C-01 API GET terhadap integration Duitku me-mask apiKey (tidak plain-text).
C-02 API GET terhadap email settings me-mask password IMAP & SMTP.
C-03 File /app/memory/*.md tidak berisi kredensial produksi.
C-04 Header Server tidak membocorkan versi nginx (server_tokens off).
C-05 Pajak selalu editable manual — bukan auto-generated tanpa opsi override.

10. Kriteria Sign-off & Kontak

10.1 Kriteria Sign-off UAT

UAT dinyatakan PASSED ketika:
  • Seluruh 60+ ceklis di Bab 9 ditandai LULUS.
  • Backend pytest suite: 0 failed, 0 errors (skipped diperbolehkan untuk test yang butuh binary sistem / live router).
  • Tidak ada regresi kritikal (P0/P1) selama 3 hari kerja stabilisasi.
  • Audit log ter-populate untuk semua aksi sensitif yang diuji.
  • Backup harian berhasil 2 hari berturut-turut & restore ter-uji minimal 1×.
